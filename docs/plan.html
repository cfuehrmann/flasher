1. Executive summary

Rewrite Flasher as a single-stack Rust application: axum backend, SQLite storage, Leptos (WASM) frontend, passkey-only auth. One build command, one binary to deploy, no Node.js anywhere, end-to-end browser tests, cargo-mutants mutation testing — closely following the conventions proven in the omega project. The old .NET/React code stays fully intact in the same repository until the rewrite is live.

The full spec this plan answers is preserved at docs/spec.md. This HTML is the living plan; update it as decisions are made and phases complete. Working conventions for contributors (human or AI) live in AGENTS.md at the repo root — it is the authoritative "how to act in this repo" and points back here.

2. Issues → remedies

Issue 1 — Dev experience & deployment

Today: two stacks (.NET 10 + Vite/React), no single start command, no shared types across the API (hand-written TS type guards in frontend/src/Api.ts), .NET required on the host.

Remedy: one Rust workspace. Shared types crate is the single contract authority for API payloads (the Omega "contract authority" pattern). One just command builds and runs everything; deployment is one static binary + one SQLite file.

Issue 2 — Data storage

Today: JSON files (cards.json per user) fully rewritten on every mutation, in-memory caches to compensate, users provisioned by hand-editing profile.json.

Remedy: SQLite — lighter than Postgres, zero server process, transactional, single-file backups, and a first-class Rust story. A built-in, idempotent migration command imports the existing JSON stores with a dry-run mode and a verification report (§4 Data & migration).

Issue 3 — Dated UX

Remedy: rebuild the UI in Leptos with a deliberate design pass (§9). Every UX change is verified with the computer-vision loop (§7) before reporting back.

Issue 4 — Dependency churn

Today: recurring GitHub vulnerability alerts, mostly transitive npm deps.

Remedy: eliminating the npm ecosystem entirely is the single biggest win — the frontend is compiled by cargo/Trunk, so node_modules disappears. On the Rust side: lean direct deps (default-features = false as a rule, no features = ["full"]), cargo machete in the gate for unused deps, cargo-deny for advisories/licenses/dupes, and exact pins with justification comments for the wasm-ABI-sensitive set — all Omega conventions.

Issue 5 — Authentication

Today: password + JWT with per-process ephemeral RSA keys (all sessions die on restart), no registration flow at all.

Remedy: passkey-only auth via webauthn-rs: register with a passkey, add/name/delete additional passkeys. Auth lives in its own crate behind a clean boundary with configurable relying-party settings, so it can later be extracted into a central passkey service for your domain without a rewrite (§4 Passkey auth).

Open decisions needs your call

D1 — Repo strategy

Recommendation: same repo. New code grows in crates/, frontends/, root Cargo.toml/justfile; old backend/ + frontend/ stay untouched until cutover, then get deleted in one commit. History and docs stay in one place; no cross-repo coordination.

Alternative: parallel repo (cleaner slate, but splits history and doubles housekeeping).

D2 — Passkey service scope

Recommendation: in-app now, extraction-ready. Auth as its own crate (flasher-auth) with a trait boundary and isolated user/credential tables. Extracting a central domain-wide passkey service later becomes a lift of one crate, not an untangling.

Alternative: defer passkeys until the central service exists (blocks issue 5 indefinitely).

D3 — SQL layer

Recommendation: sqlx, runtime-checked. Compile-time-checked queries need a live DB or offline cache during every build — a tax on every contributor/CI run. Runtime-checked keeps builds hermetic; integration tests against real SQLite provide the safety net.

Alternative: rusqlite (sync, simpler; but async sqlx fits axum better).

D4 — Frontend styling

Recommendation: hand-rolled modern CSS (custom properties, no framework) or a tiny utility layer. Replaces w3-css. No npm, no build tooling beyond Trunk, full control over the redesign.

Alternative: port a CSS framework (adds weight and churn; w3-css is part of the dated look).

4. Target architecture

Repo layout (after rewrite, old code removed)

flasher/
├── Cargo.toml                 # workspace, [lints], shared deps
├── justfile                   # build / test / run / gate / mutants
├── crates/
│   ├── flasher-types/         # CONTRACT AUTHORITY: API + domain types (serde)
│   ├── flasher-store/         # SQLite impl (sqlx), embedded migrations
│   ├── flasher-auth/          # passkeys (webauthn-rs), sessions — extraction-ready
│   ├── flasher-core/          # domain logic: SRS scheduling, search, autosave rules
│   ├── flasher-server/        # axum app: routes, static serving, lib.rs + thin main.rs
│   ├── flasher-migrate/       # JSON filestore → SQLite importer (dry-run, verify)
│   ├── flasher-auth/          # passkeys (webauthn-rs), challenges, sessions — extraction-ready
│   └── flasher-e2e/           # chromiumoxide browser harness
├── frontends/
│   └── leptos/                # DETACHED cargo workspace, lib+bin, csr/ssr features
├── docs/
│   ├── spec.md                # the original spec (preserved)
│   └── plan.html              # this file (living)
├── backend/  frontend/        # OLD .NET + React — untouched until cutover
└── scripts/                   # pre-commit hook, mutants-guard, …

Contract authority: flasher-types defines every API payload once, in Rust. Server handlers and the Leptos frontend both depend on it — API drift becomes a compile error. This delivers the "automatic type safety during usage of the Web API" the spec asks for, with no codegen step. Following Omega's loud-schema-change rule: no defensive #[serde(default)] — schema drift fails loudly, migrations handle stored data.

Domain logic lives in flasher-core, pure and DB-free: the SRS scheduling rule (currently NextTime = now + (now − ChangeTime) × multiplier with OkMultiplier=1.8, FailedMultiplier=0.5555, new-card waiting 30 min — ported verbatim from backend/Flasher.Host/Handlers/CardsHandler.cs), search, autosave semantics. Pure functions are the prime mutation-testing target.

Data & migration

Schema (SQLite):

users(id, username, created_at)
passkeys(id, user_id → users, credential_id UNIQUE, data /* serialized passkey */, name, created_at, last_used_at)
sessions(token, user_id → users, expires_at)
cards(id, user_id → users, prompt, solution,
      state CHECK(state IN ('new','ok','failed')),
      change_time, next_time, disabled)
autosaves(user_id → users PRIMARY KEY, prompt, solution, updated_at, card_id NULL)
  • Migrations: sqlx::migrate!("./migrations") embedded in the binary — runs on startup, so deployment upgrades are automatic. Roll-forward only; backups before each migration run.
  • JSON → SQLite import: flasher migrate --from ../flasher-store [--dry-run]. Idempotent (safe to re-run), prints a per-user verification report (card counts, state histogram) and exits non-zero on mismatch. The old JSON store remains the source of truth until cutover is verified.
  • SRS tunables (Cards:*) become config keys with the same defaults.
Fixture status (2026-07-27): golden test uses a synthetic fixture derived exactly from the C# FileStore schema. Additionally, the importer was validated against the real production store (mounted read-only at /home/carsten/mnt/flasher-store): 163 cards (ok=46, failed=117, 113 disabled) imported into a scratch db, verification report OK, re-run idempotent. (/home/carsten/web-site-comments/ turned out to be website-comment data, not flasher cards.)

Passkey auth

  • webauthn-rs for ceremonies; sessions are opaque tokens in a __Host-session cookie (Secure, HttpOnly, SameSite=Strict) — same cookie posture as today, but stateless secrets gone; restart-safe.
  • First-run: if users is empty, the UI offers initial registration (creates first user + first passkey). Afterwards, registration of additional users is admin-gated (single-user app today; keep it simple).
  • Passkey management screen: add a passkey, rename, delete (with "can't delete your last passkey" guard).
  • E2E-testable: Chrome DevTools Protocol virtual authenticators (WebAuthn.addVirtualAuthenticator) let the chromiumoxide harness run real registration/login ceremonies headlessly.
  • Relying-party ID/origin are config (FLASHER_RP_ID, FLASHER_ORIGIN) — the seam for a future central passkey service.

5. Testing strategy

Quality gates cost time; needless bugfixes burn tokens. The gate runs before every commit and is cheap enough to never skip:

  • Pre-commit hook as the whole CI (Omega pattern, no GitHub Actions needed): fast paths by staged-file type — docs-only skips, rust-only runs just rust-gate, frontend changes add the leptos build + snapshots, full gate adds browser e2e. Auto-cargo fmt + restage.
  • Rust gate: cargo clippy --all-targets -- -D warnings (workspace lints: clippy all+pedantic, unsafe_code = forbid, unwrap/expect/panic = warn) → nextest (with cargo-test fallback) → cargo machete (unused deps) → cargo deny check (advisories, licenses, duplicate versions).
  • Frontend gate: trunk build + host-target snapshot tests + wasm size budget check (fail if the bundle grows beyond a set threshold — keeps pulldown-cmark-style discipline).
  • Dependency hygiene: exact pins + justification comments for wasm-ABI-sensitive crates; default-features = false as the default; renovate/dependabot not needed initially — cargo deny surfaces advisories on each gate run.
  • Mutation testing stays periodic (not per-commit — it's slow by nature), run manually via just mutants-* recipes, like Omega.

7. Computer-vision verification loop

Omega's chromiumoxide harness is extended with one capability: screenshot capture.

  • just screenshots: boots server + headless Chrome, walks the key screens (login, quiz prompt, quiz solution, edit, groom, passkey settings) at desktop + mobile widths, writes PNGs to test-output/screenshots/.
  • Workflow rule for UX work: after any UI change, the agent regenerates screenshots and reads them (multimodal) before reporting back — catching layout breakage, contrast issues, overflow, and "dated look" regressions without human round-trips.
  • Optional later: committed baseline screenshots for pixel-diffing. Start without it (flaky by nature); add only if manual CV review proves insufficient.
